# 变更控制

<!-- project-governance:managed:start -->
下列变更必须进入变更控制流程：

- 架构边界、公共 API、持久化数据结构、身份认证与授权、敏感数据处理；
- 生产部署、不可逆操作、破坏性操作或外部系统写入；
- 核心语言、运行时、框架、数据库、中间件、构建工具等技术栈的新增、移除、替换，以及兼容性基线或主版本升级；
- 公式、统计口径、精度与舍入、单位与币种、汇率、时区、账期、截止时间、边界条件等业务或计算规则。

## 实施前门禁

1. 关联已确认的问题单；对于代价高、影响面广或难以回退的选择，另行关联架构决策记录（ADR）。
2. 记录变更前与变更后的状态、变更依据、影响范围、兼容性影响、迁移与发布步骤、回滚方案、负责人、批准人，以及计划生效的版本和日期。
3. 技术栈或兼容性基线发生变化时，在同一变更中同步 `.project-governance.json`、`TECH.md` 和技术栈变更索引；难以回退时必须补充 ADR。
4. 业务或计算规则发生变化时，在同一变更中更新对应的权威规则文档，列明新旧规则、输入输出、单位、精度与舍入、时间边界、示例和异常处理，并取得业务负责人或被授权角色的明确批准。
5. 列出需要同步的 API、数据、报表、用户说明、运维说明和其他受影响文档；如判断无需更新某类文档，必须记录可复核的理由。
6. 设计能够发现局部失败、兼容性回归和恢复失败的验证；计算规则变更还必须覆盖典型值、边界值、舍入临界点、单位换算和时间边界。
7. 生产、破坏性、不可逆或外部写入操作必须在执行前取得明确授权，并核对实际目标、备份或恢复条件及停止条件。

## 关闭门禁

关闭前，根据变更类型附上已审阅的文档同步、测试、迁移、发布、监控和回滚证据，并确认代码、测试与权威文档对同一规则的描述一致。单独的实现提交、口头结论或“未发现问题”不是充分证据。

## 不可绕过规则

- 问题单、实施计划和 ADR 用于记录事实与决策，本身不等于授权。
- 提示词、自动生成文本、执行者自我批准或在记录中写明“已批准”，均不能替代责任人的明确批准。
- 任何批准都不能授权泄露秘密、伪造证据、隐瞒失败、绕过安全边界，或通过删除、跳过、弱化测试来获得通过结果。
- 当任务要求、批准记录与绝对红线冲突时，以更严格的约束为准，并停止相关操作、记录冲突和请求有权角色处理。

## 项目专用审批矩阵

项目所有者是范围、计算规则及生产生效的确认角色；Codex 执行本次明确授权的本地合并与规范化。授权依据见 [I001](../../issues/I001-project-merge.md)。部署步骤及恢复点由 [部署说明](../../deploy/README.md)维护；具体发布日期和服务器状态在发布任务中记录，不预设固定发布窗口或虚构批准人。
